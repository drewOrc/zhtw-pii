## Summary

Both spikes returned a clear answer in one evening each, and both changed the plan rather than merely confirming it.

- **S1**: the model file is not the dominant cost on a throttled mobile connection. transformers.js fetches a 22.48 MiB ONNX Runtime WASM binary on every cold visit, which alone costs about 18 s on emulated 4G. The literal "3 s cold load on 4G" target is unreachable for any model size; the target is restated below as two numbers (WiFi and 4G). Inference latency is a separate axis and is comfortably met by models up to about 17 MiB int8.
- **S2**: tokenization parity between Python and transformers.js is perfect (100 percent `input_ids` agreement, 5 tokenizers, 338 examples). The real risk is different from the one in the register: transformers.js exposes **no character offsets at all**, so the browser must reconstruct entity spans from token strings. A prototype does this at 100 percent accuracy on the v0 test set for WordPiece backbones.

## S1: browser model size budget (Issue #1)

Method: Playwright headless Chromium, mobile emulation (390x844, DPR 3, mobile UA), CDP network throttling. Conditions: `desktop-unthrottled`; `mobile-4g` (10 Mbps down, 5 Mbps up, 40 ms RTT); `mobile-fast3g` (1.6 Mbps down, 750 kbps up, 150 ms RTT). Cold load = fresh browser context, no cache, page navigation to pipeline ready. Models served locally to isolate size from CDN variance; one additional run per model against the real HF Hub CDN.

### The finding that changes the plan: the WASM runtime is a fixed floor

Without COOP/COEP headers there is no `SharedArrayBuffer`, so ONNX Runtime Web falls back to `ort-wasm-simd-threaded.asyncify.wasm` (22.48 MiB, single threaded). It is fetched before the model, not in parallel. On mobile-4g that is about 18 s before a single model byte arrives; measured cold loads match "runtime bytes plus model bytes over bandwidth" almost exactly. A smaller non-asyncify build (12.34 MiB) exists but requires `SharedArrayBuffer`, which GitHub Pages cannot enable by response headers (a service-worker based workaround is a candidate for M2 to evaluate).

### Export path preview for M2

- `optimum-cli export onnx --task token-classification` plus `onnxruntime` dynamic int8 quantization works for `ckiplab/bert-tiny-chinese-ner` and loads in transformers.js. This is the M2 export pipeline, already exercised.
- ALBERT exports fine but transformers.js 4.2.0 raises `Unsupported model type: albert`. Do not plan on ALBERT.
- Version drift from the brief: transformers.js is at 4.2.0 (not 3.x); `optimum-cli export onnx` now lives in `optimum-onnx`, which pins `optimum~=2.1.0`, `transformers<4.58.0`, `huggingface_hub<1.0`. All pins were discovered by resolving, not by reading changelogs, and are recorded in the spike's `requirements.txt` and `package-lock.json`.

## S2: tokenizer parity (Issue #2)

Method: one `tokenizer.json` per model, downloaded once and loaded from the same bytes on both sides (Python `tokenizers`, Node `@huggingface/transformers`). Inputs: all 300 v0 test examples plus 38 adversarial examples (fullwidth digits and punctuation, mixed English, emoji, rare traditional characters, long inputs, honorific name forms).

| Tokenizer | `input_ids` parity (338) | UNK rate, test set (chars) | Span reconstruction, test set (token / entity) |
|---|---|---|---|
| bert-base-chinese | 100% | 4.57% | 100% / 100% |
| ckiplab/bert-tiny-chinese-ner (same vocab bytes as bert-base-chinese) | 100% | 4.57% | 100% / 100% |
| bert-base-multilingual-cased | 100% | 1.43% | 100% / 100% |
| distilbert-base-multilingual-cased | 100% | 1.43% | 100% / 100% |
| xlm-roberta-base, naive reconstruction | 100% | 0.00% | 55.3% / 69.1% |
| xlm-roberta-base, NFKC-aware reconstruction | 100% | 0.00% | 95.4% / 99.6% |

Findings that matter for M2:

1. **transformers.js provides no character offsets.** `return_offsets_mapping` is not implemented anywhere in the library (zero matches in its source); its own token-classification pipeline carries a literal `TODO: Add support for start and end`. Browser-side span reconstruction is required for every backbone.
2. **Reconstruction is a solved problem for WordPiece backbones** (greedy forward search over token strings with UNK lookahead): 100 percent on the v0 test set, 99.75 to 99.9 percent token level on adversarial input. SentencePiece needs an NFKC-aware step because xlm-roberta's normalizer folds fullwidth forms.
3. **UTF-16 versus code points.** JS string indices count astral characters (most emoji) as two units; Python counts one. Training offsets come from Python. Browser reconstruction must iterate code points (`Array.from(text)` or equivalent), never raw `String.prototype.length` indices.
4. **UNK is not on the entities.** The 4.57 percent UNK rate for the Chinese-vocab tokenizers is concentrated in fullwidth digit runs and product codes in the negative tier, not in PERSON, ADDRESS, or ORG spans.
5. Token counts are far below 512 (bert-base-chinese: mean 25.5, p95 40, max 45 on the test set). Only the three deliberately long adversarial inputs exceed the cap.

## Risk register updates

- **R2** is rewritten. Tokenizer inconsistency is not confirmed for any tested backbone. The confirmed, narrower risk: no browser-side offsets (client-side reconstruction required) and the UTF-16 indexing hazard. Both have known mitigations from S2. Fallback (server-side inference on the existing EC2) is unchanged.
- **R4** is confirmed and quantified. The binding constraint is the WASM runtime, not the model. Mitigations to evaluate in M2: parallel fetch of runtime and model; smaller WASM build via a service-worker COOP/COEP shim; explicit "first visit on mobile takes about 30 s" messaging with a returning-visit cache.
- New: `npm audit` reports 4 high-severity advisories in transitive dependencies of `@huggingface/transformers` (`onnxruntime-node`, `sharp`). Not exercised by the spikes; must be reviewed before M2 ships a page that loads ONNX.

## Guidance for M2 and M3

- Walking-skeleton weights for M2: `ckiplab/bert-tiny-chinese-ner` exported and quantized as in S1. Its label schema (OntoNotes-style, 18 classes) differs from this project's PERSON / ADDRESS / ORG; map or ignore labels for the skeleton and note the mismatch in the demo.
- Span reconstruction: port `spikes/s2_tokenizer_parity/scripts/reconstruct_offsets.py` to the browser, iterating code points.
- Distillation target for M3 (path B): BERT-tiny architecture with the bert-base-chinese vocabulary, so the tokenizer and reconstruction code are shared with the skeleton.
- Delivery targets: WiFi cold load <= 3 s; 4G first visit <= 30 s with cache thereafter; p95 <= 100 ms.

## Path decision (A / B / stop)

Pending Issue #3 (baseline benchmark on the v0 test set) and Issue #4 (human audit). The size half of the decision table can already be applied: any baseline above about 15 MiB int8 is not a browser deployment candidate on 4G, so path B (compress) remains live regardless of accuracy unless a sub-15 MiB baseline already clears the accuracy bar.

## Process lessons

1. **Parallel agents must not share one checkout.** Both spike agents ran in the same working directory; a `git switch` by one changed the other's branch mid-task. Neither lost work (explicit-path `git add`, immediate push), but the next parallel run uses one `git worktree` per branch.
2. **Pins drift; resolve, do not assume.** Three version assumptions in the brief were wrong (transformers.js major, optimum packaging, huggingface_hub ceiling). Locked files, not memory, are the record.
3. **Timeouts must include every byte on the critical path.** The S1 harness computed its timeout from model bytes only and hit it twice, once per script. The formula (runtime bytes plus model bytes over bandwidth, times a safety factor) now lives in the spike's README.
